Phiên bản 1.0 · 13/08/2026 · Bổ sung cho docs/requirements/SRS-LMS-GiangVien.md v1.0
Thay đổi lớn so với SRS: nền tảng backend chuyển từ .NET 8 → .NET 10 (LTS), kèm các điều chỉnh kiến trúc đi theo.

Tài liệu này là nguồn chân lý về kỹ thuật. SRS mô tả nghiệp vụ (giữ nguyên hiệu lực); tài liệu này mô tả cách hiện thực, và khi hai bên mâu thuẫn về mặt kỹ thuật thì lấy tài liệu này. Mọi quyết định đều ghi rõ lý do (ADR) để sau này đọc lại còn hiểu tại sao.

3. Architecture Decision Records

ADR-001 · Controllers + MediatR CQRS thay cho Minimal API

Bối cảnh: SRS mục 7 liệt kê 54 endpoint, gom sẵn thành 11 nhóm (Auth, Subjects & Versioning, Chapters & Lessons, Offerings, Groups, Assignments & Submissions, Quizzes, Final Assessments, Grades, Review Queue, Dashboard). Bản trước của ADR này chọn Minimal API theo vertical slice. Ngày 13/08/2026 người dùng chốt lại: giữ Clean Architecture 4 tầng, dùng MediatR làm xương sống CQRS, và không viết Minimal API. Quyết định dưới đây thay thế hoàn toàn bản trước; hợp đồng API không đổi một ký tự nào — cùng đường dẫn, cùng payload, cùng mã lỗi.

Quyết định: mỗi nhóm endpoint = 1 file *Controller.cs trong TeachHub.Api/Controllers/, kế thừa ApiControllerBase, gắn [ApiController] + [Route("api/…")] + [Authorize(Policy = …)] ở cấp class. Mỗi use case là một ICommand<T> hoặc IQuery<T> trong Application/Features/<Nhóm>/, đi kèm handler và validator trong cùng một thư mục.

Controller phải mỏng — đây là ranh giới cứng, không phải lời khuyên: controller chỉ định tuyến, lấy userId từ claim, gọi sender.Send(...), và quy đổi Result sang IActionResult. Không có if nghiệp vụ, không truy vấn DbContext, không try/catch. Một dòng logic lọt vào controller là một dòng không test được nếu không dựng HTTP.

[ApiController]
[Route("api/subjects")]
[Authorize(Policy = Policies.Instructor)]
[Produces("application/json")]
public sealed class SubjectsController(ISender sender) : ApiControllerBase
{
    [HttpGet]
    [ProducesResponseType<IReadOnlyList<SubjectDto>>(StatusCodes.Status200OK)]
    public async Task<IActionResult> GetAll(CancellationToken ct)
        => Ok(await sender.Send(new GetSubjectsQuery(CurrentUserId), ct));

    [HttpPost]
    [ProducesResponseType<SubjectDto>(StatusCodes.Status200OK)]
    [ProducesResponseType(StatusCodes.Status400BadRequest)]
    public async Task<IActionResult> Create(CreateSubjectCommand command, CancellationToken ct)
        => ToActionResult(await sender.Send(command with { InstructorId = CurrentUserId }, ct));
}

Hợp đồng messaging (Application/Common/Messaging/) — tách Command và Query không phải hình thức: nó là thứ để TransactionBehavior biết cái nào cần bọc transaction. Bọc query trong transaction là phí và giữ connection lâu hơn cần thiết.

using MediatR;

namespace TeachHub.Application.Common.Messaging;

/// Marker không generic để TransactionBehavior nhận diện được command.
public interface IBaseCommand;

public interface ICommand<out TResponse> : IRequest<TResponse>, IBaseCommand;
public interface IQuery<out TResponse> : IRequest<TResponse>;

public interface ICommandHandler<in TCommand, TResponse> : IRequestHandler<TCommand, TResponse>
    where TCommand : ICommand<TResponse>;

public interface IQueryHandler<in TQuery, TResponse> : IRequestHandler<TQuery, TResponse>
    where TQuery : IQuery<TResponse>;

Bảo vệ mặc định không còn dựa vào việc nhớ gắn policy cho từng nhóm route, mà dựa vào fallback policy: endpoint nào không khai gì thì vẫn đòi đăng nhập, muốn mở công khai (login, register, join code) phải viết [AllowAnonymous] tường minh.

services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build())
    .AddPolicy(Policies.Instructor,      p => p.RequireRole(Roles.Instructor))
    .AddPolicy(Policies.Student,         p => p.RequireRole(Roles.Student));

Hệ quả:

  • ✅ Mọi mối quan tâm xuyên suốt gom vào pipeline behavior, không thể sót endpoint. Log, validation, transaction chạy cho mọi request đi qua MediatR — không còn chuyện thêm endpoint mới rồi quên gắn filter. Chi tiết ở ADR-010.
  • ✅ Handler test được mà không cần dựng HTTP. Use case là một class nhận Command và trả Result; test nó bằng cách new ra rồi gọi Handle, không cần WebApplicationFactory. Integration test vẫn giữ nguyên cho tầng HTTP.
  • ✅ [ProducesResponseType] mô tả OpenAPI rõ hơn chuỗi .Produces<T>() nối đuôi: khai ngay trên action, đọc được cùng chỗ với route, và .NET 10 AddOpenApi() vẫn sinh OpenAPI 3.1 đầy đủ cho Controllers nên openapi-typescript ở frontend không đổi gì.
  • ❌ Thêm một lớp gián tiếp và thêm file cho mỗi use case — trước là 2 file (endpoint + handler), giờ là 3–4 (Command, Handler, Validator, DTO). Với 54 endpoint đây là chi phí thật, không nên giả vờ là không có.
  • ❌ Stack trace dài hơn khi debug: giữa controller và handler có ISender + ba behavior, nên exception nhìn xa nguồn hơn. Bù lại LoggingBehavior in ra tên request và thời gian chạy nên định vị vẫn nhanh.

Đã cân nhắc:

  • Giữ Minimal API + route group như bản trước. Bỏ theo yêu cầu trực tiếp của người dùng ngày 13/08/2026.
  • MediatR 14 (bản mới nhất). Bỏ vì giấy phép: từ v13 MediatR là RPL-1.5 hoặc giấy phép thương mại, mà RPL-1.5 buộc công khai mã nguồn phần mềm đã triển khai. Ghim 12.5.0 — bản Apache-2.0 cuối cùng. Đổi lại phải viết đúng API 12.x: RequestHandlerDelegate<TResponse> có một tham số CancellationToken tùy chọn (thêm từ 12.5.0), nên quy ước của dự án là gọi await next() — dạng chạy được trên mọi bản 12.x; còn khi tự khai lambda trong test thì phải viết _ => … chứ không phải () => …. Xem Phase 0 Task 0.6.
  • Bỏ MediatR, controller gọi thẳng handler class. Bỏ vì mất luôn pipeline behavior — thứ giá trị nhất của quyết định này. Không có pipeline thì transaction và validation lại phải nhớ gọi tay ở từng handler, và sẽ có handler quên.

ADR-002 · Không dùng Repository generic, MediatR handler dùng DbContext trực tiếp

Bối cảnh: SRS ghi "Controllers/Services/Repositories".

Quyết định: Application khai báo interface IAppDbContext (chỉ lộ DbSet<T> + SaveChangesAsync); Infrastructure hiện thực bằng AppDbContext : DbContext. MediatR handler viết LINQ trực tiếp trên IAppDbContext. Không có IRepository<T>.

Lý do: Repository generic bọc trên EF Core là lớp trừu tượng rỗng — nó chặn đúng những thứ ta cần (projection, Include có chọn lọc, ExecuteUpdate, split query) mà không cho lại gì. Testability đã được giải quyết bằng Testcontainers chứ không bằng mock repository (mock repository chỉ test được rằng ta gọi mock, không test được câu SQL sinh ra có đúng không).

MediatR KHÔNG phải lý do để thêm Repository trở lại. Chỗ này rất dễ trượt: thấy có CommandHandler rồi thì phản xạ quen tay là "handler thì phải gọi repository". Không. Việc chuyển từ endpoint sang ICommandHandler chỉ đổi chỗ đặt code truy vấn, không đổi lập luận ở trên: mỗi handler phục vụ đúng một use case nên nó biết chính xác mình cần cột nào, join gì, có AsNoTracking hay không — đúng thứ mà một interface generic buộc phải quên đi. Thêm IRepository<T> vào giữa handler và IAppDbContext chỉ tạo ra một tầng chuyển tiếp phải bảo trì, và sớm muộn sẽ mọc ra các hàm kiểu GetAllWithChaptersAndLessonsAndComponents() — tức là LINQ cũ, chỉ khó đọc hơn.

Ngoại lệ: nghiệp vụ phức tạp có thuật toán riêng (clone SubjectVersion, tính similarity, tổng hợp gradebook) vẫn tách thành service có interface, vì chúng cần được test độc lập và có thể thay implementation. Handler gọi service đó, không tự nhồi thuật toán vào Handle.

ADR-003 · Polymorphic FK owner_type/owner_id → 2 cột FK nullable + CHECK constraint

Bối cảnh: SRS dùng owner_type ∈ {assignment, final_assessment} + owner_id cho SubmissionSlot và Submission. Postgres không thể tạo FK cho cột đa hình → dữ liệu mồ côi là chuyện sớm muộn.

Quyết định: giữ nguyên owner_type (để code đọc/lọc thuận tiện, và giữ đúng hợp đồng API trong SRS), nhưng lưu bằng 2 cột FK thật:

assignment_id        uuid NULL REFERENCES assignments(id)        ON DELETE CASCADE,
final_assessment_id  uuid NULL REFERENCES final_assessments(id)  ON DELETE CASCADE,
owner_type           text NOT NULL,
CONSTRAINT ck_slot_owner CHECK (
  (owner_type = 'assignment'       AND assignment_id IS NOT NULL AND final_assessment_id IS NULL) OR
  (owner_type = 'final_assessment' AND final_assessment_id IS NOT NULL AND assignment_id IS NULL)
)

Hệ quả: DB tự bảo vệ toàn vẹn, xóa Assignment tự dọn slot/submission. API vẫn nhận/trả owner_type + owner_id đúng như SRS mục 7 — quy đổi ở tầng mapping.

ADR-005 · Xử lý ZIP trong Hangfire queue riêng, có giới hạn cứng

  • Zip-slip: chuẩn hóa đường dẫn entry, từ chối nếu thoát khỏi thư mục đích.
  • Zip bomb: chặn cứng tổng dung lượng sau giải nén (mặc định 200 MB), số entry (5.000), tỉ lệ nén tối đa (100:1) — vượt là hủy job, gắn cờ cho giảng viên xem.
  • Magic bytes: kiểm tra chữ ký file thật (PK\x03\x04 cho zip, v.v.) chứ không tin phần mở rộng — đúng yêu cầu NFR "validate loại file thực tế".
  • Không bao giờ thực thi nội dung giải nén; chỉ đọc để dựng file_tree_json và hiển thị text.

Nâng cấp về sau (P2): đẩy hẳn worker unzip sang container riêng có --read-only, giới hạn CPU/RAM, không có network.

ADR-008 · Sổ điểm cấu hình động: bộ cột mẫu, quy tắc tổng hợp, điểm cộng có đích

Bối cảnh: SRS chỉ mô tả GradeColumn phẳng gắn một source_type, như thể mọi lớp đều dùng chung một bộ cột. Thực tế không phải vậy. Một môn mặc định hai cột "Thường kỳ" + "Cuối môn"; môn khác lại ba cột "Trắc nghiệm" + "Bài tập" + "Cuối môn". Tỷ lệ giữa các cột thay đổi theo đề cương từng năm, và cách gộp điểm bên trong một cột cũng khác nhau: cột "Bài tập" ở môn này là trung bình 8 bài, ở môn kia là bỏ 2 bài thấp nhất rồi mới lấy trung bình. Người dùng chốt ngày 13/08/2026: phải "config động" được bộ cột, công thức, tỷ lệ và cấu hình xuất điểm, kèm khả năng cộng điểm vào bất kỳ cột nào. Hard-code hai cột vào schema là tự chặn đường ngay từ lớp đầu tiên.

Quyết định: tách thành bốn phần rời nhau, mỗi phần chịu trách nhiệm đúng một việc.

  • Thư viện bộ cột mẫu, cấp giảng viên — GradeSchemeTemplate(instructor_id, name, is_default, order_index) kèm GradeSchemeTemplateItem(key, name, weight_percent, order_index, aggregation). Soạn một lần ("2 cột chuẩn", "3 cột có trắc nghiệm"), dùng lại cho mọi môn, mọi học kỳ.
  • Ghim mẫu mặc định ở SubjectVersion — SubjectVersion.grade_scheme_template_id (uuid nullable, FK). Đặt ở SubjectVersion chứ không phải Subject, vì tỷ lệ điểm thuộc về đề cương và được phép đổi theo năm học. SubjectVersionCloner (Phase 1) chỉ copy FK này, không deep clone mẫu — mẫu thuộc về giảng viên chứ không thuộc nội dung môn học, khác hẳn Chapter/Lesson/Assignment ở ADR-004. Deep clone mẫu sẽ sinh ra hàng chục bản sao rác trong thư viện sau vài học kỳ.
  • Mở lớp thì SAO CHÉP cột vào offering — GradeColumn(offering_id, key, name, order_index, weight_percent, aggregation) + GradeColumnSource[], unique index (offering_id, key). Chép xong, cột của lớp độc lập hoàn toàn với mẫu. CourseOffering.grade_scheme_template_id chỉ ghi nhận nguồn gốc để hiển thị, không tham gia tính điểm.
  • Quy tắc gộp điểm khai báo, không phải biểu thức — GradeAggregation lưu jsonb trong cột, chọn từ một danh sách đóng 8 kiểu. Không có ô nhập công thức tự do ở bất kỳ đâu.
public enum AggregationKind
{
    Manual,            // nhập tay hoàn toàn, không tự tổng hợp
    Average,           // trung bình cộng các nguồn
    WeightedAverage,   // dùng GradeColumnSource.WeightWithinColumn
    Sum,               // cộng dồn rồi kẹp [0,10]
    Max, Min,
    DropLowestN,       // bỏ N điểm thấp nhất rồi trung bình
    BestNOfM,          // lấy N bài tốt nhất rồi trung bình
}

public sealed class GradeAggregation
{
    public AggregationKind Kind { get; set; } = AggregationKind.Average;
    public int N { get; set; }
    public bool TreatMissingAsZero { get; set; } = true;
}

Kèm theo là GradeCondition (jsonb, cấp offering) cho điều kiện điểm sàn — ColumnKey, Op ∈ {LessThan, LessOrEqual}, Threshold, Action = CapFinalAt, ActionValue — đủ để diễn đạt quy định phổ biến ở đại học Việt Nam: "Cuối môn < 4.0 thì điểm tổng tối đa 3.9". Và điểm cộng có đích: BonusPoint.target ∈ {FinalTotal, GradeColumn} + target_column_id (CHECK constraint ràng hai trường với nhau), points bắt buộc > 0, reason NOT NULL độ dài > 0, template_id nullable trỏ tới BonusPointReasonTemplate. Offering giữ ba mặc định (bonus_default_target, bonus_default_column_id, bonus_max_points_per_student) để giảng viên không phải chọn lại mỗi lần.

Thứ tự tính điểm trong GradebookCalculator (thuần Domain, không I/O) là bản chốt, thay thế mọi mô tả cũ:

1. rawColumn[c] = IsManualOverride ? GradeRecord.Score
                                   : c.Aggregation.Apply(normalizedSourceScores)
   -- normalizedSourceScores: MỌI nguồn quy về thang 10 TRƯỚC khi gộp
      normalized = raw / sourceMaxScore * 10
2. ledger = BonusLedger.Build(bonuses, settings)   -- xem ADR-009
3. columnScore[c] = clamp(rawColumn[c] + ledger.ByColumnId[c], 0, 10)
4. total = Σ(columnScore[c] × weight/100) + ledger.ToFinalTotal
5. total = ApplyConditions(total, columnScore, conditions)   -- cap điểm sàn
6. total = clamp(round(total, 1, AwayFromZero), 0, 10)

ADR-009 · BonusLedger: chốt sổ điểm cộng một lần trước khi tính

Bối cảnh: bản thiết kế trước để mỗi hàm tính điểm tự xử lý danh sách bonuses thô. Đây là loại lỗi không ai phát hiện cho tới khi sinh viên in bảng điểm ra đối chiếu và thấy con số hôm nay khác hôm qua.

Quyết định: đưa ra một kiểu bất biến đã "chốt sổ" điểm cộng, chỉ tạo được qua Build. Mọi hàm tính điểm nhận BonusLedger, không hàm nào được nhận danh sách bonus thô.

/// Kết quả đã áp trần và sắp xếp tất định. Chỉ tạo qua BonusLedger.Build.
/// Mọi hàm tính điểm nhận Ledger này, không nhận danh sách bonus thô — nhờ đó

{

    public required decimal ToFinalTotal { get; init; }

    /// MaxBonusPerStudent MỘT LẦN trên toàn bộ tập bonus.

ADR-010 · Pipeline behavior là nơi duy nhất đặt mối quan tâm xuyên suốt

Bối cảnh: ba việc lặp lại ở mọi use case — ghi log request, kiểm tra dữ liệu đầu vào, bọc transaction cho thao tác ghi. Cách cũ là mỗi handler tự lo, hoặc gắn filter cho từng nhóm endpoint. Cả hai đều thất bại theo cùng một kiểu: người viết use case thứ 46 quên mất một trong ba thứ đó, và không có gì báo lỗi — code vẫn biên dịch, test vẫn xanh, chỉ có một thao tác ghi không còn nguyên tử.

Quyết định: ba behavior, thứ tự đăng ký chính là thứ tự chạy từ ngoài vào trong — Logging → Validation → Transaction → Handler.

// TeachHub.Application/DependencyInjection.cs
services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssembly(assembly);
    cfg.AddOpenBehavior(typeof(LoggingBehavior<,>));      // 1. tên request + thời gian + userId
    cfg.AddOpenBehavior(typeof(ValidationBehavior<,>));   // 2. FluentValidation
});
services.AddValidatorsFromAssembly(assembly);

// TeachHub.Infrastructure/DependencyInjection.cs — đăng ký SAU hai cái trên
services.AddTransient(typeof(IPipelineBehavior<,>), typeof(TransactionBehavior<,>));  // 3.

Vì sao Validation phải chạy TRƯỚC Transaction: nếu đảo lại, mỗi request có dữ liệu sai vẫn mở một transaction trên Postgres, chạy validator, ném exception, rồi rollback một transaction chưa làm gì cả. Với một form nhập điểm mà người dùng gõ sai liên tục, đó là hàng loạt connection bị giữ vô ích chỉ để rollback. Thứ tự đúng thì request sai bị chặn khi chưa hề chạm tới database.

public sealed class TransactionBehavior<TRequest, TResponse>(AppDbContext db)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        if (request is not IBaseCommand) return await next();            // query: không bọc
        if (db.Database.CurrentTransaction is not null) return await next();

        await using var tx = await db.Database.BeginTransactionAsync(ct);
        var response = await next();
        await tx.CommitAsync(ct);
        return response;

}

Lưu ý MediatR 12.5.0: RequestHandlerDelegate<TResponse> có một tham số CancellationToken tùy chọn, nên cả await next() lẫn await next(ct) đều biên dịch được. Quy ước dự án là await next(): nó chạy đúng trên mọi bản 12.x (12.0–12.4 delegate không có tham số nào) và vẫn chuyển token gốc xuống handler. Chỗ dễ vấp là khai lambda trong test — () => … ném CS1593, phải viết _ => …; xem Phase 0 Task 0.6.

Vì sao TransactionBehavior nằm ở Infrastructure chứ không phải Application: nó cần DbContext.Database.BeginTransactionAsync. Đặt ở Application sẽ buộc Application tham chiếu EF Core — phá đúng ranh giới tầng mà Clean Architecture sinh ra để giữ. Behavior của MediatR không bắt buộc nằm cùng tầng với handler: đăng ký ở đâu cũng chạy, vì nó chỉ là một IPipelineBehavior<,> trong DI container. Cách né duy nhất còn lại là dựng một interface IUnitOfWork giả trong Application chỉ để giữ hình thức — thêm một lớp trừu tượng không ai dùng ngoài chính nó, đúng thứ ADR-002 đã từ chối.

Hệ quả cụ thể — SubjectVersionCloner ở Phase 1 không còn phải tự mở transaction. ADR-004 yêu cầu deep clone chạy trong một transaction; bản plan cũ vì thế phải thêm BeginTransactionAsync vào IAppDbContext (làm interface lộ chi tiết EF) rồi tự mở/commit/rollback trong cloner. Giờ CloneSubjectVersionCommand là ICommand, nên behavior đã bọc sẵn: cloner chỉ còn việc clone. Yêu cầu nguyên tử vẫn y nguyên, chỉ là không còn viết tay ở từng chỗ. Điều tương tự áp cho mọi command đụng nhiều bảng: mở lớp (sao chép GradeColumn từ mẫu), import Excel danh sách sinh viên, chấm hàng loạt.

Hệ quả: ✅ Thêm use case mới không phải nhớ gì cả — chọn đúng ICommand hay IQuery là ba behavior tự áp dụng. ✅ Muốn thêm mối quan tâm mới (audit, cache, retry) thì thêm một behavior, không sửa 54 chỗ. ❌ Behavior chạy ngầm nên người mới đọc code sẽ không thấy transaction ở đâu — bù bằng chính ADR này và một dòng comment ở DependencyInjection. ❌ Behavior sai một chỗ là sai toàn hệ thống, nên bản thân behavior phải có test riêng.

Đã cân nhắc: để mỗi handler tự BeginTransaction khi cần. Bỏ vì đó chính là kỷ luật-thay-cho-kiểu-dữ-liệu mà ADR-009 đã bác: sẽ có handler quên, và triệu chứng là dữ liệu ghi dở dang — loại lỗi chỉ lộ ra khi đã hỏng.

ADR-011 · Hai mô hình lỗi: exception cho validation, Result cho kết quả nghiệp vụ

Bối cảnh: một use case hỏng theo hai kiểu rất khác nhau, và trộn chúng vào một cơ chế là nguồn gốc của phần lớn code xử lý lỗi rối rắm. Kiểu thứ nhất: dữ liệu gửi lên không hợp lệ — thiếu tên môn, trọng số âm, email sai định dạng. Kiểu thứ hai: nghiệp vụ trả về một kết quả không phải thành công — không tìm thấy môn, version đã publish rồi nên không sửa được nữa, giảng viên A đụng vào lớp của giảng viên B.

Quyết định:

  • Lỗi dữ liệu đầu vào → exception. FluentValidator ném ValidationException trong ValidationBehavior, một IExceptionHandler toàn cục bắt và đổi thành 400 + ValidationProblemDetails. Lý do: loại lỗi này không bao giờ cần xử lý riêng theo từng use case — không có chỗ nào trong hệ thống muốn "bắt lỗi email sai định dạng rồi làm việc khác". Đã vậy thì gom về một chỗ là đúng, và handler sạch hẳn.
  • Kết quả nghiệp vụ mong đợi → Result. Không tìm thấy, xung đột trạng thái, không có quyền — giữ nguyên kiểu Result đã dùng ở các plan Phase 1–4b. Lý do: chúng là một phần hợp đồng của use case, phải hiện ra trong chữ ký hàm để người gọi buộc phải xử lý, không được giấu vào exception. "Publish một version đã publish" là một nhánh nghiệp vụ có thật, không phải sự cố.

ApiControllerBase có hai overload ToActionResult: bản Result (không mang giá trị) trả NoContent() khi thành công, bản Result<T> trả Ok(result.Value). Mọi nhánh lỗi đi qua Problem(...) — cố ý không dùng NotFound() / Forbid(), vì Problem luôn trả application/problem+json theo RFC 9457 kèm detail đọc được, còn Forbid() trả 403 với thân rỗng và frontend không có gì để hiển thị cho người dùng. Nhờ vậy controller không cần biết gì thêm và vẫn giữ được yêu cầu "không try/catch trong controller" ở ADR-001. Hiện thực đầy đủ ở Phase 0 Task 0.7.

Rủi ro nếu trộn lẫn — đây là lý do phải viết ADR riêng cho một chuyện tưởng là vặt: khi cùng một loại lỗi lúc thì ném exception, lúc thì trả Result, lập trình viên không còn cách nào biết khi nào phải try/catch, khi nào phải kiểm Result. Kết cục quen thuộc là làm cả hai cho chắc — try/catch bọc quanh một lời gọi vốn đã trả Result, rồi bên trong lại quên kiểm IsFailure. Lúc đó lỗi "không tìm thấy" âm thầm đi tiếp như thể thành công, và thứ nổ ra là một NullReferenceException cách đó ba tầng gọi hàm — không ai lần ngược được về nguyên nhân. Ranh giới phải rạch ròi: đầu vào sai thì ném, nghiệp vụ không thành thì trả.

Đã cân nhắc: dùng exception cho cả hai (NotFoundException, ConflictException, ForbiddenException đều ném, handler toàn cục đổi mã HTTP). Ngắn hơn thật, nhưng khi đó chữ ký handler nói dối: nhìn Task<SubjectDto> tưởng luôn có kết quả, trong khi nó có ba đường thoát ngầm. Ba lớp exception đó chưa được tạo và không task nào trong Phase 0–4b tạo chúng — cố ý: mọi nhánh "không tìm thấy / xung đột / không có quyền" đã có Result lo, nên tạo sẵn một thư mục Common/Exceptions/ rỗng chỉ là lời mời quay lại ném exception cho nhánh nghiệp vụ. Khi nào gặp ca thực sự bất thường đầu tiên — dữ liệu vi phạm bất biến của chính hệ thống, tức là bug chứ không phải người dùng nhập sai — thì mới thêm lớp exception cho đúng ca đó, kèm một dòng trong IExceptionHandler.

ADR-012 · Nhiều giảng viên độc lập, cách ly bằng quyền sở hữu tài nguyên

Bối cảnh: SRS mục 2 viết cho một giảng viên là chủ hệ thống. Người dùng xác nhận muốn nhiều giảng viên nhưng độc lập — không cộng tác, không đồng sở hữu môn, không chia sẻ thư viện (13/08/2026).

Quyết định: mọi tài nguyên gắn instructor_id trực tiếp hoặc gián tiếp qua Subject/CourseOffering; mọi truy vấn lọc theo chủ sở hữu ngay trong câu truy vấn. Tài khoản sinh ra bằng lời mời (InstructorInvite), không mở đăng ký công khai; người đầu tiên qua POST /api/auth/bootstrap chạy đúng một lần rồi khoá vĩnh viễn. Tài nguyên không thuộc người gọi luôn trả 404, không bao giờ 403.

Hệ quả: ✅ không cần vai trò Admin — mời người khác vào không cấp thêm quyền cho ai; ✅ thêm giảng viên không ảnh hưởng dữ liệu của ai; ❌ không chia sẻ được rubric hay thư viện giữa các giảng viên, chấp nhận vì đó chính là mức cộng tác đã bị loại bỏ; ❌ mỗi handler phải tự lọc, nên bắt buộc phải có ma trận CrossInstructorIsolationTests (Phase 0 Task 0.8c) — một endpoint quên lọc là lộ điểm số và bài nộp của lớp người khác, mà loại lỗi này không có triệu chứng nào.

Đã cân nhắc: (a) OfferingStaff cho trợ giảng/đồng giảng — hoãn sang P2 theo lựa chọn của người dùng; (b) mở đăng ký công khai — bỏ vì bất kỳ ai trên internet cũng tạo được tài khoản giảng viên rồi tiêu dung lượng máy chủ; (c) thêm vai trò Admin — bỏ vì ở quy mô vài đồng nghiệp, một vai trò và mấy màn hình quản trị chỉ để mời người là không đáng.

ADR-013 · Vai trò trợ giảng khai báo sẵn nhưng tắt hoàn toàn ở MVP

Bối cảnh: SRS mục 2 có vai trò Teaching Assistant. Bản plan trước đã khai Roles.TeachingAssistant và Policies.InstructorOrTa — nhưng không có bảng nào gắn trợ giảng vào một lớp cụ thể, trong khi mọi kiểm quyền viết dạng subject.InstructorId == currentUserId.

Vấn đề thật: hai kết cục, không có mức trung gian. Hoặc trợ giảng không làm được gì (vì không sở hữu môn nào), hoặc — nếu nới điều kiện cho họ chấm được — họ chấm được ở mọi lớp của mọi giảng viên. Một policy đang cấp quyền cho vai trò chưa có cách giới hạn theo lớp là lỗ hổng nằm chờ.

Quyết định: giữ hằng số Roles.TeachingAssistant (để bật lại không phải migrate), xoá Policies.InstructorOrTa khỏi phần đăng ký và khỏi mọi endpoint, và thêm một test canh gác: tài khoản chỉ mang vai trò trợ giảng phải bị từ chối ở mọi endpoint nghiệp vụ.

Hệ quả: test canh gác đỏ ngay nếu ai đó về sau vô tình thêm lại policy — rẻ hơn nhiều so với phát hiện lúc một trợ giảng đã xem được sổ điểm lớp khác. Bật lại cần OfferingStaff(offering_id, user_id, role) và chuyển toàn bộ kiểm quyền sang resource-based; phần đắt không phải bảng quan hệ mà là sửa lại mọi handler đã có test. Xếp ở P2.

5. Quy ước bắt buộc khi code

Đặt tên

  • DB: snake_case, bảng số nhiều (subject_versions).
  • C#: PascalCase, entity số ít (SubjectVersion).
  • Ánh xạ tự động bằng UseSnakeCaseNamingConvention() của Npgsql — không viết tay từng HasColumnName.
  • JSON API: snake_case (khớp SRS mục 7), cấu hình một lần bằng JsonNamingPolicy.SnakeCaseLower — với Controllers thì đặt trong AddControllers().AddJsonOptions(...). Đặt nhầm chỗ là API trả camelCase và frontend hỏng toàn bộ mà không có lỗi nào rõ ràng.

Command / Query & controller

  • Đặt tên: <Động từ><Danh từ>Command (CreateSubjectCommand, PublishVersionCommand, ImportEnrollmentsCommand) và Get<Danh từ>Query (GetSubjectsQuery, GetGradebookQuery). Handler là <Tên>Handler, validator là <Tên>Validator.
  • Mỗi use case một thư mục chứa đủ Command + Handler + Validator (+ DTO nếu riêng), dưới Features/<Nhóm>/Commands/<TênUseCase>/ hoặc .../Queries/<TênUseCase>/. Sửa một chức năng = mở đúng một thư mục.
  • Thao tác ghi phải khai ICommand<T>, thao tác đọc khai IQuery<T> — không phải hình thức: TransactionBehavior dựa vào đó để quyết định có bọc transaction hay không (ADR-010). Khai nhầm query thành command là giữ connection vô ích; khai nhầm command thành query là mất tính nguyên tử.
  • Controller không được chứa logic nghiệp vụ. Chỉ định tuyến, lấy userId từ claim, sender.Send(...), quy đổi Result bằng ToActionResult. Không if nghiệp vụ, không đụng DbContext, không try/catch. Review thấy vi phạm là trả lại, không du di.

Kiểu dữ liệu

  • Điểm: decimal(5,2) — không dùng double ở bất cứ đâu liên quan tới điểm.
  • Thang điểm duy nhất là số 0–10: mọi điểm (điểm cột, điểm tổng, điểm sau khi cộng bonus) đều kẹp trong [0, 10] bằng clamp, hiển thị 1 chữ số thập phân. Không có thang điểm chữ ở bất kỳ đâu — API, sổ điểm, file Excel đều chỉ trả về số.
  • Trọng số: decimal(5,2), đơn vị phần trăm.
  • Id: Guid tạo bằng Guid.CreateVersion7(), không để DB tự sinh.
  • Thời gian: DateTimeOffset (không dùng DateTime).
  • Enum lưu xuống DB: mọi enum đều khai .HasConversion<string>().HasMaxLength(32); giá trị chuỗi trong CHECK constraint phải khớp đúng tên enum C# ('GradeColumn'), không dùng snake_case ('grade_column'). EF mặc định map enum ra integer, nên viết CHECK bằng chuỗi mà quên khai HasConversion là migration chết ngay lúc apply. Quy ước này áp cho toàn bộ enum của dự án, nhất quán với các enum đã có ở Phase 1–3 và cho BonusTarget, AggregationKind, ConditionOperator, CapAction, GradeExportSource.

Test

  • Luật nghiệp vụ (tính điểm, unlock, late penalty, clone) → unit test ở Domain.Tests, chạy < 1 ms.
  • Use case (handler + validator) → unit test ở Application.Tests: new handler rồi gọi Handle, không dựng HTTP. Pipeline behavior cũng phải có test riêng — sai một behavior là sai toàn hệ thống.
  • Endpoint (controller + auth policy + serialization) → integration test thật với Postgres container.
  • Mỗi task trong plan bắt đầu bằng test đỏ. Không có ngoại lệ cho code tính điểm.

Bảo mật

  • Mọi endpoint mặc định đòi đăng nhập nhờ fallback policy (SetFallbackPolicy + RequireAuthenticatedUser); mở public phải gắn [AllowAnonymous] tường minh.
  • Truy cập dữ liệu lớp luôn qua policy resource-based (SV chỉ thấy offering mình học, giảng viên chỉ thấy môn mình tạo).
  • Upload: rate limit + giới hạn dung lượng + kiểm tra magic bytes phía server.
